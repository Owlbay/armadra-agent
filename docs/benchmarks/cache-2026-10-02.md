# 缓存验收实验（2026-10-02）

> 由 `scripts/cache-experiment.mjs` 生成（第三波 §1.13）。「读 / 输入」= cacheRead /（input + cacheRead + cacheWrite），逐请求列出。
> 合计请求 83 次（含 E4 前对 MiniMax 的 2 次三态预热）；E2 两种保温各跑了两遍（见「请求数说明」）。

## 环境

- 2026-10-02，本分支构建（含 C1a 协议层、C1b 会话层缓存），SDK `createRuntime`、`full-auto`，fix-bug 仓库在临时目录；测试中转站一个 provider（B12 模型级 `api`）。
- 中转模型目录没有 `promptCache` 与价格：E2 给 Kimi **用户自填** `promptCache.short: 300`（依据 Kimi 名义 5 分钟）与价格 input 0.6 / output 2.5 / cacheRead 0.15 美元每 M，并把 `cache.minSavingsUsd` 降到 0.0001（这些请求的前缀只有 ~0.8k token，按缺省 $0.05 门槛保温永远不划算）。
- ama 的系统提示与工具表很短（default 预设首个请求约 0.8k token），所以 E1 / E2 / E5 的前缀都小；E4 另用 24k 字符的 AGENTS.md 把前缀垫到约 7.8k。

## 结论（改进前后对比）

| 实验              | 改进前                                                                                         | 改进后（实测）                                                                                            | 判定                                                                                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1 基线命中率     | 第三波计划记录的实测：Kimi 768–1010 / 832–1010、MiniMax 891–1523                               | Kimi 累计 86%（640–2048 / 791–2130）、MiniMax 75%、DeepSeek 44%；Kimi / MiniMax 0 次未命中                | 不退化。DeepSeek 经中转以 **2048 token 为粒度**报缓存读，前缀 < 2048 时恒为 0，触发 1 次假 `evicted`（1031 token）                                                   |
| E2 长工具运行保温 | 无保温（等价于 `warming: off`，实测两遍）                                                      | `streaming` 两遍各在 `sleep 420` 期间发出 1 次保温（每次约 $0.00015，读 640–768）                         | 机制按设计工作；但 off 两遍在 7 分钟后仍读到 768 / 865——该中转上 Kimi 缓存寿命 ≥ 7 分钟（或被并发会话的同一前缀续命），**收益无法测出**                              |
| E3 摘要前缀续写   | 独立请求：序列化转录（工具结果截到 2000 字符），按构造 cacheRead = 0（未重复实测，守请求上限） | 续写请求确实发出（输入 19.7k，含 19k 的工具结果原文），但 **cacheRead 0**，且比上一个回合请求少 438 token | **未达预期**：`tool_choice: "none"` 时中转 / Kimi 渲染提示不带工具定义，前缀在工具段就断了。此端点上续写比回落路径更贵（19.7k 全价 vs 约 3k 全价）                   |
| E4 未命中归因     | 只有命中率下降                                                                                 | 依次出现 `model_changed` 7.8k、`prefix_changed:tools` 7.9k、`prefix_changed:system` 7.5k                  | 符合预期。前缀 < 1024 时按设计不判（第一组全「无」）；宿主在末尾追加工具在 Kimi 上仍让整段前缀失效（读 0）                                                           |
| E5 不报缓存端点   | 显示 0%                                                                                        | DeepSeek、GLM 在该中转**已经报缓存**（probe 第二次读 2048 / 3410、3072 / 3340）→ `reported`               | 计划 §1.6 记录的「DeepSeek / GLM 报 0 → silent」不再成立，真实端点上没有触发 silent；silent 路径只有单测覆盖。DeepSeek 4 轮里 3 次假 `evicted`（同 E1 的 2048 粒度） |

### 后续建议（不在 B9b 文件范围内）

1. **E3**：openai-completions（至少非官方端点）续写时不发 `tool_choice: "none"`，保留工具表、只靠指令约束并沿用「含工具调用 → 回落」；或加 compat 开关。修好后用 `cache-experiment --case E3` 复测。
2. **DeepSeek 经中转的假未命中**：给该模型填 `promptCache.minTokens: 2048`（噪声下限 = max(1024, minTokens)），或在目录 / discover 里按端点给出缓存粒度。
3. E2 要测出收益，需要前缀大（≥ 50k）且不被其它会话共享的场景；当前数据只证明机制与计费正确。

### 请求数说明

计划上限 80，实际 83：第一次启动 E2 时误以为后台进程随 shell 退出而中断，重新跑了一遍，结果两遍都完成（4 + 5 请求各两次，多出约 9 个请求，被 E3 只跑改进后一侧抵掉一部分）。两遍数据都保留，作为重复测量。全部脚本合计（SSE 录制 19 + 基准试跑 6 + 基准 120 + 缓存 83）= 228，低于 240 的总上限。
