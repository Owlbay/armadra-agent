说明：

- **`--version` / `-p`**：收益来自全局命令改指 bundle（D7）与 `Intl.Segmenter` 惰性（bundle 本身 78.9 → 76.7 MB）。报告的 `-p` 一轮 92–98 MB 本来就是 bundle 口径，原目标「≤ 92」在噪声边缘（之后 92.7），按全局命令口径改为 ≤ 98。
- **`-p --resume` 55 MB 仍 218 MB 的构成**：进程基线约 80 MB（node + bundle 代码与字节码）；V8 堆 `heapTotal` 约 130 MB，其中可达对象 78 MB——**66 MB 是解析出的转录字符串本身**（会话文件 57 MB，toolResult 正文占绝大部分），其余约 50 MB 是逐行解析留下、尚未整理的堆空间；external 只剩 7 MB（不再有整文件 Buffer / 字符串）。再往下降要么不把整段转录常驻（旧 toolResult 正文按需从文件回读，牵涉 P2-4 与 rewind / fork），要么在加载后主动整理堆，都超出本波范围；目标按实测改为 ≤ 220 MB。
- **mock HTTP 带图 720 MB**：M-B 单独测得 689 MB（中位），本次 720 MB 在同一量级（本机负载更高、样本 3 次）；剩余主要是每次请求仍要对整段上下文做一次投影与编码（P2-1）、以及同一时刻多出的一份图片 UTF-8 片段（见遗留）。目标改为 ≤ 720 MB，「≤ 650」留给步骤二（按消息缓存片段）。
- **ACP ext 16.3 MB（已解决）**：当时全部 close 后剩下的是**启动会话**——第一个 `session/new` 认领进程启动时建的会话，`Runtime.session` 固定持有它到进程退出，关闭只能 dispose 不能释放。#165 把 `Runtime.session` / `Runtime.sessionManager` 改为跟随当前会话，并切断 bootstrap 闭包对启动会话的引用；遗留项批次复测 close + GC 后 heap 14.9 / **ext 7.0 MB**，目标回到 ext ≤ 10（见 R）。
- **RPC**：D9 有意保留 `message_end` 与 `tool_execution_end` 两份正文（前者是客户端替换整条消息的依据，后者带 `details`），5 份里留 2 份，下限就是 40%；原目标「≤ 30 MB（−65%）」与 D9 不自洽，改为 ≤ 原来的 45%。
- 「之前」与报告的差异：`read-huge` 774 / 757、`list` 541 / 486 在同一量级；`mock-http` 无图 670 MB 明显高于报告的 366–487 MB，是因为脚本里的读取每次给 2000 行（约 50 KB），请求体最大 8.8 MB、共 1.3 GB，比报告的驱动程序（最大 3.5 MB、共 573 MB）重得多，两者不可直接比。

### 发现

1. **mock HTTP 无图的峰值 RSS 在 M-E 合入后上升约 90 MB**（逐个合并提交二分：`b217ed1` / `056e5ce` / `0cbf468` 为 672–707 MB，`e8ac513` 起 751–794 MB）。**结论（#172，见 R「#172 归因」）**：不是留存，是 macOS 分配器（libmalloc）对已释放大块的缓存——这个场景峰值 RSS 里约 330 MB 是它，`MallocLargeCache=0` 下三个构建都回到 379–408 MB；M-E 让主 GC 次数从约 71 次降到约 29 次，ArrayBuffer 底层内存释放得更晚、同时在用的大块更多，缓存随之变大。#171 改为异步读之后差额只剩约 15 MB（噪声量级），目标按此修订。
2. `bench-memory.mjs rpc-bytes` 的读取端在 ama 输出被截断时会直接抛 `JSON.parse` 错误（只在人为压低堆上限、ama 中途退出时出现过一次）；只影响测量脚本。已由 #173 修复（坏行计数、中途退出不挂起）。

### #172 归因：mock HTTP 无图

四个构建：`0cbf468`（#162 前）、`e8ac513`（#162，字节窗口同步读）、`699720b`（当前 main）、以及当前 main 的 bundle 把 `STREAM_READ_THRESHOLD` 改成 `Infinity`（同一份代码只换回整读路径，请求体完全相同）。除注明外每格 3 次中位数，`node scripts/bench-memory.mjs mock-http --images 0 --runs 3 --entry <bundle>`。

| 构建                 |      峰值 RSS | heapUsed | heapTotal | external |   other | 主 GC 次数（`--trace-gc`） | `--max-old-space-size=128` 峰值 RSS | `MallocLargeCache=0` 峰值 RSS / other |
| -------------------- | ------------: | -------: | --------: | -------: | ------: | -------------------------: | ----------------------------------: | ------------------------------------: |
| `0cbf468`（#162 前） | 689.5 / 697.7 |       94 |   138–141 |       98 | 541–545 |               70 / 71 / 74 |                               557.3 |                         379.0 / 152.1 |
| `e8ac513`（#162）    | 759.6 / 778.4 |  102–112 |   120–127 |   93–107 | 585–601 |               29 / 29 / 30 |                               607.4 |                         408.1 / 175.9 |
| `699720b`（main）    | 706.5 / 709.4 |    92–93 |   116–117 |    88–93 | 542–557 |               34 / 34 / 35 |                               560.0 |                         381.9 / 170.6 |
| main + 整读路径      | 689.5 / 697.0 |       94 |       140 |       98 | 508–548 |                          — |                                   — |                                     — |

单次 `vmmap -summary`（`AMA_MEM_VMMAP_AT=3000`，约在运行中段）：`MALLOC_LARGE (empty)` `0cbf468` 149 MB、`e8ac513` 229 MB、main 235 MB；`MALLOC_SMALL (empty)` 40 / 56 / 58 MB；V8 堆（heapTotal）只有 74–108 MB。

结论：

1. **不是留存**。差额全在 other 列（V8 堆与 external 之外），vmmap 显示是分配器里**已释放、未还给系统**的大块（`MALLOC_LARGE (empty)`）。关掉 libmalloc 的大块缓存（`MallocLargeCache=0`）后三个构建峰值都回到 379–408 MB、other 降到 150–176 MB；退出时的堆快照留存在 Z 时已确认相同。
2. **为什么 #162 让它变大**：旧路径每次读取都分配整文件字符串与切行数组，主 GC 约 71 次；字节窗口几乎不分配，主 GC 降到约 29 次。请求体分块、SSE 响应缓冲等 ArrayBuffer 的底层内存要等主 GC 才释放，GC 间隔变长 → 同时在用的大块更多 → 分配器缓存的空闲大块更多。老生代压到 128 MB（强制更频繁的主 GC）时 main 与 `0cbf468` 相同（560 / 557 MB）。
3. **当前状态**：#171 改为异步读之后 main 比 `0cbf468` 只高约 10–15 MB，与「main + 整读路径」的差同量级，在本机 ±5% 噪声内（`0cbf468` 自身 689–720 MB）。原目标 ≤ 670 MB 是 Z 时 `0cbf468` 的单组中位数，今天同一构建测得 690–698 MB，不再作为回归线。
4. **处置**：记录为预期，不在库代码里设 V8 / 分配器参数；`docs/design.md` §9.2 该行改为 ≤ 730 MB 并注明分配器缓存。设计 §8 步骤 2 的 `--text-mb 0.5` 对照没有采用：小文件会让脚本里大部分 `offset` 越过文件末尾、请求体随之变小，改用只换阈值的 bundle 对照。步骤 5–6（分配剖析、缓冲复用）不再需要：读路径本身的差额已在噪声内。
