## Z：`bench-memory.mjs` 全场景复测

- **之前** = `04c7bc2`（契约批次 M-C0 与 #135 已合入、内存各批次都未合入），**之后** = `8ac3b20`（M-A…G 全部合入）。两份 bundle 用当前的 `scripts/bench-memory.mjs` 交替跑，每项 3 次取中位数：
  `node scripts/bench-memory.mjs --runs 3`（之前加 `--entry <旧 bundle>`；全局命令口径加 `--entry <旧 dist/cli/main.js>`）。
- 「报告」列是报告 §2 的原始数字（测量方法与参数略有不同，只作量级对照）；目标列是 [memory-plan.md](../memory-plan.md) §4 修正后的目标。

| ------------------------------------------- | ------------------- | ------------------------------------ | ----------------------------------------- | -------------------- | ----------------------------- |

说明：

- **`--version` / `-p`**：收益来自全局命令改指 bundle（D7）与 `Intl.Segmenter` 惰性（bundle 本身 78.9 → 76.7 MB）。报告的 `-p` 一轮 92–98 MB 本来就是 bundle 口径，原目标「≤ 92」在噪声边缘（之后 92.7），按全局命令口径改为 ≤ 98。
- **`-p --resume` 55 MB 仍 218 MB 的构成**：进程基线约 80 MB（node + bundle 代码与字节码）；V8 堆 `heapTotal` 约 130 MB，其中可达对象 78 MB——**66 MB 是解析出的转录字符串本身**（会话文件 57 MB，toolResult 正文占绝大部分），其余约 50 MB 是逐行解析留下、尚未整理的堆空间；external 只剩 7 MB（不再有整文件 Buffer / 字符串）。再往下降要么不把整段转录常驻（旧 toolResult 正文按需从文件回读，牵涉 P2-4 与 rewind / fork），要么在加载后主动整理堆，都超出本波范围；目标按实测改为 ≤ 220 MB。
- **mock HTTP 带图 720 MB**：M-B 单独测得 689 MB（中位），本次 720 MB 在同一量级（本机负载更高、样本 3 次）；剩余主要是每次请求仍要对整段上下文做一次投影与编码（P2-1）、以及同一时刻多出的一份图片 UTF-8 片段（见遗留）。目标改为 ≤ 720 MB，「≤ 650」留给步骤二（按消息缓存片段）。
- **ACP ext 16.3 MB**：全部 close 后剩下的是**启动会话**的转录与图片——第一个 `session/new` 认领进程启动时建的会话，它由 `Runtime.session` 持有到进程退出，关闭只能 dispose 不能释放（M-A 遗留）。被关闭的其它 7 个会话全部回收（`acp-release.test.ts` 断言实例数、控制面注销与 external 回到基线）。原目标「ext ≤ 10」在 fake 场景受这一个会话影响，改为 ≤ 20 并写明原因；真实 astr 纯文本场景 ext 7.0 MB（见 A）。
- **RPC**：D9 有意保留 `message_end` 与 `tool_execution_end` 两份正文（前者是客户端替换整条消息的依据，后者带 `details`），5 份里留 2 份，下限就是 40%；原目标「≤ 30 MB（−65%）」与 D9 不自洽，改为 ≤ 原来的 45%。
- 「之前」与报告的差异：`read-huge` 774 / 757、`list` 541 / 486 在同一量级；`mock-http` 无图 670 MB 明显高于报告的 366–487 MB，是因为脚本里的读取每次给 2000 行（约 50 KB），请求体最大 8.8 MB、共 1.3 GB，比报告的驱动程序（最大 3.5 MB、共 573 MB）重得多，两者不可直接比。

### 发现

1. **mock HTTP 无图的峰值 RSS 在 M-E 合入后上升约 90 MB**（逐个合并提交二分：`b217ed1` / `056e5ce` / `0cbf468` 为 672–707 MB，`e8ac513` 起 751–794 MB；`rpc-bytes` 的 heapUsed 峰值同样由约 55 MB 升到约 130 MB）。已排除的原因：① 不是留存——两者退出时的堆快照可达对象 20.6 / 22.0 MB、构成相同；单独对 4 MB 文件读 300 次，字节窗口路径的峰值 RSS 反而更低（203 → 134 MB），留存相同；② 把 V8 老生代上限压到 64 MB 后 `rpc-bytes` 两者都是约 182 MB，说明 heapUsed 峰值是**未回收的垃圾**：旧路径每次读取都分配整文件字符串与切行数组，这些分配推动了更频繁的主 GC，新路径分配极少，主 GC 间隔变长；③ 但把老生代压到 128 MB 时 mock HTTP 仍差约 115 MB（538 / 654 MB），差额不在 V8 堆与 external 的采样里；在字节窗口里每次补一个 4 MB 的 Buffer 制造外部内存压力、或把逐行复制改成直接解码，都不能消除差额。结论：是 GC 节奏 / 原生分配器层面的峰值变化，不是泄漏；需要单独剖析（建议新 Issue，见 PR 遗留项）。
2. `bench-memory.mjs rpc-bytes` 的读取端在 ama 输出被截断时会直接抛 `JSON.parse` 错误（只在人为压低堆上限、ama 中途退出时出现过一次）；只影响测量脚本。

## T：TUI 带图会话（astr/gpt-6-luna，10 次请求）

tmux 驱动交互界面，同一个工作区（3 张 900×900 噪声 PNG，每张 2.4 MB，base64 3.2 MB），前后两个构建各跑一次同样的 4 个提示、5 次请求：`@img0.png` 描述、`@img1.png` 描述（自动附图）、比较两图（无工具）、让模型用 `read` 读 `img2.png` 并报尺寸（一次工具调用）。探针 250 ms 采样，峰值 RSS 取 `process.resourceUsage().maxRSS`。

| 构建              | 峰值 RSS     | heapUsed 峰值 | external 峰值 | 退出时 RSS / heap / ext |
| ----------------- | ------------ | ------------- | ------------- | ----------------------- |
| 之前（`04c7bc2`） | 275.5 MB     | 61.2 MB       | 53.4 MB       | 173.5 / 14.8 / 19.3 MB  |
| 之后（`8ac3b20`） | **218.4 MB** | **33.7 MB**   | **28.6 MB**   | 144.4 / 15.6 / 16.3 MB  |

峰值 RSS −21%，heap 与 external 峰值约减半。报告的 392 MB 是 8 个提示、19 次请求、2 张图（含多次工具读图）的更长会话，本次受请求次数上限只跑了它的约四分之一，不能直接对照；同场景前后对照与 M-B 的结果（下文 B）方向一致，目标「≤ 300 MB」按两组数据判为达成。

## A：ACP 释放（M-A，#161）

`acp-pool`（fake，8 会话 × 4 轮，每会话 4 次读图）。M-A 当时 fake 还会留住每次请求的上下文（M-F 的 D12 之前），前后对照都临时用不留上下文的 fake 构建：

| acp-pool | 打开 + GC heap / ext | 关闭 + GC heap / ext | 峰值 RSS |
| -------- | -------------------: | -------------------: | -------: |
| 修改前   |      21.9 / 105.9 MB |      22.0 / 105.9 MB | 386.9 MB |
| 修改后   |      21.9 / 105.9 MB |   **13.7 / 19.3 MB** | 393.9 MB |

关闭后剩下的 ext 约 19 MB 是启动会话（见 Z 的说明）。图片驻留（M-D）合入后，同一张图在各会话之间也共享，Z 表里「打开 + GC」的 ext 从 105.9 降到 16.3 MB。

真实 astr/gpt-6-luna（8 次请求，4 会话 × 2 轮纯文本，全部 `end_turn`）：

| 时点               | heapUsed | external |             RSS |
| ------------------ | -------: | -------: | --------------: |
| initialize 后 + GC |  10.1 MB |   5.3 MB |         85.9 MB |
| 2 轮后 + GC        |  15.7 MB |   7.0 MB |        119.3 MB |
| 全部 close + GC    |  15.5 MB |   7.0 MB |        119.3 MB |

heap ≤ 20 MB、external ≤ 10 MB（报告基线 16 / 7），无回归。

## B：请求体序列化（M-B，#163）

`mock-http`（300 步、15 次读图、260 次请求、请求体最大 24.7 MB、共 3 786 MB；交替各 3 次）：

|                      |                                  峰值 RSS |   峰值 heapUsed |   峰值 external |               用时 |
| -------------------- | ----------------------------------------: | --------------: | --------------: | -----------------: |
| 前（含 M-D 的 main） | 1 073.6 / 1 043.1 / 1 023.8（中位 1 043） | 165 / 165 / 180 | 150 / 179 / 179 | 12.4 / 8.5 / 8.2 s |
| 后                   |   688.9 / 683.2 / 717.8（中位 689，−34%） | 180 / 218 / 245 |  91 / 114 / 108 |  8.2 / 8.1 / 8.1 s |

按设计原样接线（`body: Buffer`）时同场景反而升到 1 854 MB：Node 的 fetch 会把 BufferSource 请求体再复制两份，因此改为以流 + 准确 `content-length` 发送（不走 chunked）。heapUsed 采样峰值上升是外部内存压力变小后主 GC 间隔变长，RSS 是实际占用。

真实 astr/gpt-6-luna（TUI，提示里点名的图自动附上，共 10 次请求）：

| 场景                                  | 前 峰值 RSS / heapUsed | 后 峰值 RSS / heapUsed |
| ------------------------------------- | ---------------------- | ---------------------- |
| 3 个提示、2 张 2.4 MB PNG（3 次请求） | 220.4 / 40.7 MB        | 187.3 / 35.1 MB        |
| 2 个提示、2 张图（2 次请求）          | 197.7 / 40.7 MB        | 168.8 / 28.3 MB        |
