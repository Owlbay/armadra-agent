# 缓存实验 E6：自动压缩（2026-10-02）

> 第五波 W5-H1（docs/wave5-plan.md §8.4）。由 `scripts/cache-experiment.mjs --case E6` 生成数据（`cache-e6-2026-10-02.json`），下面的「数据」一节是 `--render` 的原样输出。「读 / 输入」= cacheRead /（input + cacheRead + cacheWrite）。
> 合计 **83 次请求**（含 3 次中转报错后自动重试的空请求），按预算脚本的保守口径（输入与缓存读都按 $1 / M、输出 $4 / M）计 **$1.11**，按 Kimi 名义价（输入 0.6、缓存读 0.15、输出 2.5 美元 / M）约 **$0.33**；中转的真实账单未单独核对。没有打印或记录 key。

## 环境

- 2026-10-02，本分支构建（W5-H1 全部改动）对照 main 194b6ba 构建（「现状」，`--dist`）；SDK `createRuntime`、`full-auto`、`cache.warming: off`；测试中转站 `packy/kimi-k2.5`，该端点报缓存（三态 `reported`）。
- 模型窗口用配置改成 **40k**（预算 = 40k − 16 384 预留 ≈ 23.6k：档一触发 16.5k、目标 11.8k、`clearAtLeast` auto 4.7k、保护 4.7k），让一条提示里读 12 个约 12 KB（≈ 3k token）的文件就能跨过档一 / 档二阈值；中转目录没有 TTL，用户自填 `promptCache.short: 300`。
- 第一组：一条提示里逐个读 12 个文件（单提示长任务，G1 的形态），停 330 s 后再读一个；三种构建各一遍。`C1+C2` 是本分支把 `isCold()` 换成恒 false（关掉冷时提前裁）。
- 第二组（专看 C3）：只读 3 个文件（停在档一阈值以下）、`compaction.prune.keepResults: 1`，停 330 s / 720 s 后再读一个；`C1+C2` 与 `C1+C2+C3` 各一遍。
- 每组只跑一遍，模型自己决定调用次数（第一组 C1+C2+C3 多调了 5 次），单次差异有噪声；结论只取方向一致、幅度明显的部分。

## 结论

| 问题                                      | 实测                                                                                                                                                                                                            | 判定                                                                                                                                      |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 单提示长任务里档二能否多次摘要（G4 / C5） | 现状一条提示内只摘要 1 次（`run_limit`），之后上下文涨到 **34.1k，超出预算 23.6k 的 44%**（真实 40k 窗口下再读两个文件就溢出）；C1+C2 同一提示内摘要 2 次，最大 22.4k，始终在预算内                             | 修复有效                                                                                                                                  |
| C1+C2 对缓存与费用                        | 同样 17 次请求：cacheRead 占比 65% → **73%**，全价输入 104.5k → **72.7k**（−30%），Kimi 名义价 $0.0936 → **$0.0755**（−19%）                                                                                    | 不打断缓存，反而更省（上下文更小、没有现状那次 30k 的中途淘汰）                                                                           |
| 档一在单提示里是否生效（G1）              | 第一组 C1+C2+C3 在第 17 个请求裁了 2 个旧结果（16.5k 阈值），裁后那一回合只读到 2.2k（前缀从裁剪点断开），下一回合起恢复 99% 命中；第二组 C1+C2 在跨阈值时同样一次裁 2 个                                       | 生效；一次裁够、之后不再逐回合推进（每组各 1 批）                                                                                         |
| C3 冷时提前裁                             | 第二组：停顿后 C1+C2+C3 先裁再发，首个请求 5.7k（读 1.3k）；C1+C2 不裁，首个请求 13.6k（读 13.6k，100%），但下一回合跨过阈值照样要裁、照样重写。合计输入 53.2k → **45.3k**（−15%），请求 8 → 7，Kimi 名义价 −7% | 本例净省；但见下一行                                                                                                                      |
| TTL 判断是否准                            | 该中转上 Kimi 的缓存停 **720 s 后仍 100% 命中**（第三波 E2 已见 ≥ 7 分钟）；用户自填的 300 s 比实际短，C3 判「冷」时缓存其实还热                                                                                | C3 只在 TTL 准确时才是「零额外代价」；本例省钱靠的是「反正很快要裁」。中转目录没有 `promptCache` 时 `isCold()` 按隐式 10 分钟，仍可能偏早 |
| §9.1 前缀稳定                             | 两个 C 构建在没有裁剪 / 摘要的回合之间都是 99–100% 命中、0 次归因未命中；现状有两次中途读 0（归因 `evicted`，中转侧淘汰，与改动无关）                                                                           | 不破坏前缀稳定（`src/cli/cache-stability.test.ts` 照常通过）                                                                              |

建议：`clearAtLeast` 保持 auto；C3 保留（实测净省），但在报告里记下「TTL 偏短会让 C3 丢掉还热的缓存」，等有官方端点（TTL 有承诺）时再测一次 `C1+C2` 与 `C1+C2+C3` 的长停顿对比。
