## 结论

1. **线上形状合规**：134 条消息（4 份黄金记录 43 行 + 实测 `ama --mode acp` 91 行）逐条用官方 schema 校验，**0 失败**。
   ama 发出的 initialize / session/new|load|resume|list|close|set_mode|prompt 响应、全部 `session/update`、`session/request_permission`、错误对象都合规。
2. **覆盖面是 v1 的“核心 + 2026 会话生命周期”子集**：13 个 agentMethods 实现 8 个（缺 `authenticate`、`logout`、`session/set_config_option`、`session/delete`；`session/cancel` 已做）；
   11 种 SessionUpdate 发 8 种（缺 `available_commands_update`、`config_option_update`、`session_info_update`）；
   客户端方法只用 `session/update`、`session/request_permission`（fs/terminal/elicitation 有意不用）；`$/cancel_request` 两侧都没做。
3. **在 Zed 里真正会碰到的问题**（按严重度）：
   - 一个进程只有一个活动会话：Zed 多线程共用一个连接，**运行中开新线程/切线程报 busy**；**切回一个还没发过消息的线程报 -32002 会话不存在**（实测复现）。
   - **未配置模型时进程直接以退出码 4 结束**，Zed 只能显示“服务器退出”+ stderr 尾巴；没有走 ACP 的 `auth_required` / 终端登录流程。
   - **codemode 内层调用的权限请求带一个从未公布过的 toolCallId**（实测是随机 UUID），Zed 会为它新建一个工具条目，之后再无更新，永远停在待定状态。Node ≥ 25 时 default 预设缺省开 codemode。
   - **文件编辑不发 `diff` 内容**，Zed 看不到改动 diff，只有一行“Edited a.txt: 1 replacement”。
   - 模型 / 思考级别不可在 Zed 里切换（没有 config options），斜杠命令（skills、提示模板）不出现在 Zed 补全里（没有 available_commands）。
4. **规范 MUST 偏离（有意设计，但需在文档里说明）**：`cwd` 固定为启动目录（规范要求 MUST 使用客户端给的 cwd）；不连接客户端给的 stdio MCP 服务器（规范要求所有 Agent MUST 支持 stdio MCP）。Zed 本地单根项目下 cwd 一致，实际影响小。
5. **客户端侧（ama 驱动外部 Agent）**稳健性良好：未知 sessionUpdate 静默忽略、畸形通知不致崩溃、只认 Agent 自己给的 optionId、取消时挂起的权限回 cancelled。缺口在 `auth_required`（-32000）没有引导、不支持 config options（只靠 `modes`）、不处理入站 `$/cancel_request`、diff 内容的路径不计入改动文件。

### 2.3 ToolCall 字段与权限

- 字段：toolCallId ✅、title ✅、kind ✅、status ✅、content 🟡（只有 text）、locations ✅（绝对路径，无 line）、rawInput ✅、rawOutput ❌、**name ❌**、`_meta` ❌。
- **diff ❌**：edit 工具手里有改前/改后全文（`src/tools/edit.ts:254-256` 生成 `details.diff` 统一 diff），write 工具只有 `bytes/created`（`src/tools/write.ts:77-83`），都没转成 ACP `{type:"diff", path, oldText, newText}`。
- 权限选项：`allow_once` / `allow_always`（名为“本会话允许”，语义比规范的“记住”窄，但 kind 正确）/ `reject_once`（`acp-server.ts:341-345`）。无 `reject_always`，可接受。Zed 按 kind 渲染按钮，匹配。
- **顺序偏差**：`tool_execution_start` 先于审批，所以客户端先看到 `in_progress` 再收到权限请求（实测）。规范：pending =“输入流式中或等待批准”，批准后 SHOULD 再报 in_progress（prompt-turn.mdx:257）。Zed 会把状态覆盖成等待确认，影响小。
- **codemode 孤儿 toolCallId（实测）**：`acp-server.ts:324-325` 先按工具名+参数找已公布的调用，找不到退回 `request.requestId`；codemode 内层调用从不公布（`acp-events.ts:141,149`），所以权限请求总是带新 UUID。Zed `request_tool_call_authorization` → `upsert_tool_call_inner` 对未知 id 新建条目（`zed acp_thread.rs:5245-5290, 5610-5650`），之后无更新，条目一直悬挂。

### 2.6 错误码

用到 -32600（busy）、-32601、-32602、-32603、-32002（会话不存在）。没用 -32000（auth_required）、-32800（request cancelled）。均合规，但 -32000 是 Zed 唯一会引导用户登录的入口（`zed acp.rs:1900-1902, 2002-2010`）。

### 2.7 cwd 与会话模型

- cwd 固定为启动目录（`acp-server.ts:14, 99, 106, 186-191`），理由：信任与项目配置按启动 cwd 判定（`cli/bootstrap.ts:119-130`）。偏离 session-setup.mdx:363 的 MUST，**有意**。
- 一次只有一个活动会话（`acp-server.ts:4-7, 93-95`）：切换前 `ensureIdle`（`:265-268`），运行中新建/切换报 -32600 busy；空会话不落盘，切走后 `switchSession(resume)` 找不到 → -32002（实测）。

## 4. Zed 实际可用性风险（读代码判断，附置信度）

配置写法（Zed 文档 external-agents.md）：

```json
"agent_servers": { "ama": { "type": "custom", "command": "ama", "args": ["--mode", "acp"], "env": {} } }
```

| 风险               | 判断                                                                                                                                                                                                                                                          | 置信度                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| cwd                | Zed 本地项目以第一个 worktree 根作进程 `current_dir`（`zed transport.rs:28-71`），`session/new` 也传同一路径（`acp.rs:1476-1495`），ama realpath 比较通过。远程项目经 `build_command(root_dir)` 也一致。**无 worktree 的空窗口**下进程 cwd 不确定，可能不一致 | 高（本地）/ 中（空窗口） |
| stdout 污染        | ama 自己没有（实测）。`takeOverStdout` 在 bootstrap 之后才接管（`cli/bootstrap.ts:461-462`），bootstrap 期间用户级 host/hook 的 `console.log` 理论上会写 stdout；非交互默认不信任项目，项目 hooks 不加载                                                      | 高 / 低                  |

## 5. 建议实施清单

### P0（Zed 基本流程会出错）

1. **多会话支持**（至少修 -32002）。`acp-server.ts` 改为维护 `Map<sessionId, AgentSession>`，或最少：空会话切走时保留内存对象/立即落盘，切回时不走 `resume` 查盘；允许不同会话并发运行或对非活动会话排队而不是 busy。涉及 `src/modes/acp/acp-server.ts`（主体）、`src/cli/compose-session.ts`（是否支持多会话并存）、`acp-events.ts`（mapper 按会话）、`acp-mode.test.ts`。规模：中到大（300–600 行）。最小修复（空会话切回）：小（~50 行）。
2. **无模型也能完成握手**。`--mode acp` 下模型解析失败不退出：`initialize` 正常回并给 `authMethods`（`type: "terminal"`，args 如 `["auth","login","chatgpt"]` 或引导 `ama auth set`，仅在客户端声明 `auth.terminal` 时给），`session/new`/`prompt` 回 -32000 并带说明；登录后重新解析模型。涉及 `src/cli/bootstrap.ts`、`src/cli/startup-steps.ts`（`resolveModel` 延迟化）、`acp-server.ts`、`drivers/acp/types.ts`（AuthMethod 类型）、`docs/acp.md`。规模：中（150–300 行）。

### P1（体验明显差或偏离稳定规范）

3. **codemode 内层调用对齐 toolCallId**：内层调用也发 `tool_call`/`tool_call_update`（可用 `_meta` 标父调用），或权限请求的 toolCallId 指向外层 codemode 调用并把内层信息放进 title/rawInput。涉及 `acp-events.ts`、`acp-server.ts:324-325`。规模：小到中（50–120 行）。

5. **Session config options**：`model`（category `model`）、`thinking`（`thought_level`）、`mode`（category `mode`，与 `modes` 同步）；实现 `session/set_config_option` 与 `config_option_update`；boolean 只在客户端声明 `session.configOptions.boolean` 时发。涉及 `acp-server.ts`、`acp-events.ts`、`drivers/acp/types.ts`、i18n 文案。规模：中（150–250 行）。
6. **available_commands_update**：会话开始/切换后公布 skills（`skill:<name>`）、提示模板、少量可在 ACP 下执行的内置命令（如 compact）。涉及 `acp-events.ts`/`acp-server.ts`、`src/skills/*` 只读接口。规模：小到中（60–120 行）。
7. **tool_call `name`**（已稳定）：`emitToolCall` 加 `name`；类型补字段。涉及 `acp-events.ts:224-235`、`drivers/acp/types.ts:252-261`。规模：极小（<10 行）。
8. **出站 `$/cancel_request`**：`JsonRpcPeer.request` 被 abort 时发 `$/cancel_request {requestId}`（可选开关，Codex app-server 侧不发）；入站 `$/cancel_request` 对挂起请求回 -32800。涉及 `src/drivers/jsonrpc.ts`、`drivers/acp/types.ts`（错误码 -32800）。规模：小（40–80 行）。
