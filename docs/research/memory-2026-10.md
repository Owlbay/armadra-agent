# ama 内存占用测量与优化报告（0.7.3，2026-10-10）

> 范围：启动、TUI、`-p`、ACP、RPC 各模式的峰值与常驻内存，泄漏与无界增长点，以及优化清单。只读调研：测量时仓库没有改动，构建产物与驱动脚本放在仓库外的临时目录；之后把可复现的场景整理进 [`scripts/bench-memory.mjs`](../../scripts/bench-memory.mjs)（采样探针 [`scripts/lib/mem-probe.cjs`](../../scripts/lib/mem-probe.cjs)），下文的「复现」都指向它。
> 真实模型请求：astr 共 27 次（TUI 19 次 + ACP 8 次）；chatgpt 订阅共 9 次（TUI）。配置目录用真实的、数据目录是隔离的；key 由 ama 在内部解析，没有读取 auth.json。
> 本文是 [memory-plan.md](../memory-plan.md) 的依据，只用于追溯；代码行号对应写作时的 `main`，现状以代码与 `docs/` 其余文档为准。设计对本报告的异议与修正见 memory-plan.md 文末。

## 结论

1. **基线不重，长会话和大输入才是问题。** bundle 冷启动约 77–81 MB RSS（裸 `node -e 0` 约 50 MB），TUI 空闲 84–101 MB，空闲期间不增长。bundle 体积（2.85 MB）只带来约 5 MB 的源码字符串和 2–5 MB 字节码，精简体积对 RSS 的影响在噪声范围内。
2. **最大的峰值来自「每次请求都把整个上下文序列化成一个大字符串」。** 走真实 HTTP 路径（本地 mock 的 Responses SSE 服务）跑 300 步、带 7 张约 3 MB 的图：请求体最大 21.9 MB，345 次请求共发 4.5 GB，`postJson` 一共分配约 13 GB（约为请求体的 3 倍），峰值 RSS **1.19 GB**。不带图时峰值是 366–487 MB。用真实模型（astr/gpt-6-luna）跑 8 个提示、19 次请求、2 张图，峰值就到了 **392 MB**。
3. **`read` 读大文件会整文件进内存。** 读 255 MB 日志的前 100 行，峰值 RSS 是 **757 MB**；同一个文件用 `grep` 只有 98 MB，用 `bash cat` 是 196 MB。
4. **ACP 的 `session/close` 关闭后会话释放不掉（泄漏）。** 8 个会话各跑 4 轮后全部关闭并强制 GC，仍有 90–98 MB external（全部图片）和 9 个 `_AgentSessionImpl` 留在内存里。原因是每次 `session/prompt` 挂的 abort 监听从不移除，它挂在 `AbortSignal.any` 合成的信号上，只要连接还在，这个信号就一直存活。
5. **图片 base64 在内存里完全不去重，被裁剪或压缩后也不释放。** 3 个文件读 15 次就有 15 份 3.09 MB 的字符串（46 MB）。在交互界面里，提示词里提到图片路径会自动附图，模型再用工具读一次，同一张图就存了两份。
6. **会话文件整读整解析。** 恢复一个 55 MB 的会话峰值 333 MB（`-p`）或 358 MB（TUI）。`sessions list` 扫 4 个 55 MB 文件峰值 **486 MB**，交互的恢复选择器和 ACP `session/list` 走的是同一条路径。
7. 全局安装的 `ama` 命令指向未打包的 ESM（`dist/cli/main.js`，487 个文件），比 bundle 多约 24–28 MB RSS，启动时间约是 bundle 的 2 倍。

## 1. 测量方法

- 所有 fake 场景都把 `HOME`、`AMA_CONFIG_DIR`、`AMA_DATA_DIR` 指向临时目录下的新目录；工作区是 4.3 MB 文本、3 张 900×900 随机噪声 PNG（每张 2.4 MB，base64 后 3.2 MB）、50 个源文件。`bench-memory.mjs` 沿用这套隔离（子进程环境从零构造，不带任何 API key）。
- 采样：`/usr/bin/time -l` 取最大 RSS；用 `--require` 预加载探针，每 200–500 ms 记录一次 `process.memoryUsage()`，并支持退出时写堆快照和分配采样（inspector `HeapProfiler.startSampling`，包含已被 GC 回收的分配）。TUI 用 tmux 驱动，ACP 和 RPC 用自写的驱动程序。仓库版探针另在退出时记 `process.resourceUsage().maxRSS`，跨平台取峰值。
- **fake 供应商有测量干扰**：`FakeProvider.calls` 会记住每次请求的完整上下文（`src/ai/fake/fake-provider.ts:215`），300 步时独占 31.7 MB。因此长会话测量用的是只把这一行改成 `push({ index })` 的临时 bundle，其余与安装版逐字节相同（设计 D12 之后不再需要）。
- **真实 HTTP 路径**用本地 127.0.0.1 的 OpenAI Responses SSE 模拟服务：按 fake 脚本回放，并记录每次请求体的字节数。配置是隔离目录里的自定义供应商 `mock/m1`（openai-responses，窗口 1M），key 用占位值。`bench-memory.mjs mock-http` 内置了同一个服务。
- macOS 注意事项：空闲时 RSS 会因为内存压缩下降，例如 101 MB 降到 84 MB，恢复会话时甚至出现 RSS 小于 heapUsed+external 的情况。所以下文以 `time -l` 的峰值和 heap/external 为准，空闲 RSS 只作参考。
- 节点版本：Node 26.10.0，macOS（Darwin 25.6）。

顺带发现一个功能问题（与内存无关，Issue #139）：ACP 下，某个会话的上一轮派生了后台子 Agent，通知它的后续轮次还在跑时，又来了这个会话的 `session/prompt`，返回的是 `-32603 "a run is in progress; pass streamingBehavior or use steer()/followUp()"`，而 `docs/acp.md` 说的是「排队」。8 个会话 × 4 轮的 fake 复现里出现了 2 次。

## 6. 优化清单

约束提醒：零依赖、单文件 ≤600 行、提示前缀字节稳定、会话文件格式兼容、rewind/resume 语义不变。#135（模型调用效率）正在改 session-cache、压缩、子 Agent、重试相关代码；涉及这些文件的条目需要和它协调（交集与先后见 memory-plan.md §3.0）。

### P0

**P0-1 `read` 按需流式读取大文件**

- 问题与证据：G1。读 255 MB 文件的前 100 行，峰值 757 MB；4 GB 的日志足以把进程撑爆。
- 方案：文件大于阈值时改走流式路径。分块读，用 `Buffer.indexOf(0x0a)` 定位行；只解码 `[offset, offset+limit)` 范围内、不超过 50 KB 的内容；`totalLines` 继续扫描换行计数，不构造字符串；二进制嗅探只看前 8 KB（现在的 `SNIFF_BYTES`）。小文件保持现有路径，输出逐字节不变。
- 涉及文件：`src/tools/read.ts`；新建 `src/tools/read-lines.ts`，以免超过 600 行。
- 预期节省：大文件读取的峰值从约 3 倍文件大小降到约 1 MB 以内。255 MB 的例子省约 650 MB。
- 风险：CRLF、BOM、UTF-8 跨块边界需要处理，测试覆盖「跨块的行」和「末尾无换行」。（设计 D1 把阈值从报告建议的 8 MB 改为 1 MiB。）

**P0-2 修 ACP 关闭后的会话泄漏（L1，顺带 L2、L3）**

- 问题与证据：见第 5 节。Armadra 以长连接的 ACP 嵌入 ama，会话开了又关，内存只增不减。
- 方案：`acp-server.ts` 的 `prompt()` 给 abort 监听保存引用，在 `await result` 的 finally 里 `removeEventListener`；`reporting.ts` 的 `last` 只保存比较需要的字段；核对 `session/close` → `disposeSessionAlongside` 是否调用了 `SubagentRegistry.dispose()` 和 `unregisterTaskControl`。
- 涉及文件：`src/modes/acp/acp-server.ts`、`src/drivers/jsonrpc.ts`、`src/ai/cache/reporting.ts`、`src/cli/` 下的 dispose 组装。
- 预期节省：每个被关闭的会话的全部转录（本测试中 8 个会话约 90 MB，真实场景按会话体积线性增长）。
- 风险：低。补测试：开 N 个会话、关闭后用 WeakRef + `--expose-gc` 断言可以被回收。

**P0-3 请求体序列化降到约 1 倍请求体**

- 问题与证据：G4。13 GB 分配 / 4.5 GB 请求体；22 MB 的请求体每次瞬时占用约 65 MB 以上；mock 的峰值 1.19 GB。
- 方案（报告原稿）：各协议转换器对「已进入上下文且不可变」的消息，用 WeakMap 缓存「消息对象 → 序列化后的 Buffer 片段」，组装请求体时按原来的键序拼接，作为 `Buffer` 交给 fetch。（设计 D3 的修正：消息身份在请求层不稳定，第一步改为不碰转换器的分块序列化器。）
- 涉及文件：`src/ai/http.ts`、`src/ai/apis/*`。
- 预期节省：图片多的会话峰值降低 40–60%（1.19 GB 那组场景中估计能省 300–500 MB，需要复测）；CPU 也随之下降。
- 风险：中。字节稳定性要用黄金请求体逐字节比对守住。

### P1

**P1-1 图片 base64 按内容哈希驻留**

- 问题与证据：G3。3 个文件读 15 次就有 15 份（46 MB）；交互界面自动附图再加工具读图，同一张图存两份。
- 方案：进程级维护「sha256 → 图片」的弱引用表，覆盖 `readImage`、`--image` / `@图片` 附件、会话加载这三个入口。会话文件和请求体都不变。（设计 D5：`WeakRef` 不能指向字符串，改以 `ImageBlock` 为驻留单元。）
- 涉及文件：`src/tools/read.ts:102`、`src/tools/image-file.ts`、会话加载处。
- 预期节省：本测试 37 MB（15 份降到 3 份）；真实会话中每张重复读的图省 1×。
- 风险：低。

**P1-2 列会话不再整读整解析**

- 问题与证据：G2。4 个 55 MB 文件峰值 486 MB；交互恢复选择器和 ACP `session/list` 都受影响。
- 方案：`SessionManager.list` 读头部拿到 header 和首条提示；`messageCount` 用 `lineType()` 分块流式计数，不调用 `JSON.parse`；`forEachLine` 改成分块读取，回调返回 false 时立即停止。
- 涉及文件：`src/session/manager.ts:152-175`、`src/session/scan.ts:85-102`。
- 预期节省：列表的峰值从 O(总字节 × 数倍) 降到 O(块大小)，本例省约 400 MB，耗时也明显下降。
- 风险：低到中。`messageCount` 的口径要与现在一致，写测试对照。

**P1-3 恢复会话改为流式解析**

- 证据：55 MB 的会话 `-p --resume` 峰值 333 MB。
- 方案：`readSessionLines` 按块读、按行 `JSON.parse`，不再生成整个文件的字符串和 `split` 结果数组；repair 逻辑（末尾半行）保持不变。
- 涉及文件：`src/session/store.ts:66-110`。
- 预期节省：恢复峰值减少约一半，本例约 100–150 MB。
- 风险：低。格式和语义都不变。

**P1-4 全局 `ama` 命令改走 bundle**

- 证据：ESM 版 105 MB / 0.17 s，bundle 版 77 MB / 0.09 s；`-p` 为 116 MB 对 98 MB。
- 方案：`package.json` 的 `bin.ama` 指向 `dist/bundle/ama.cjs`（它自带 shebang，已经 `chmod 755`）；库导出（`.`、`./host` 等）仍然用 ESM。
- 预期节省：每个进程约 20–28 MB，启动时间减半。
- 风险：`--host` 加载 ESM 适配器、`import.meta.url` 相关路径要在 bundle 下走一遍端到端；发布检查需要相应调整。

**P1-5 子 Agent 会话的 LRU 上限 16 → 4，或闲置时释放转录**

- 证据：`src/agent/subagent-registry.ts:75`（`DEFAULT_RETAINED = 16`）。快照中有 17 个 SessionManager；真实子 Agent 的转录通常有几 MB 到几十 MB。
- 方案：调低默认值，或者句柄闲置超过 N 分钟就 dispose（JSONL 还在，按现有的「续聊时重开」逻辑重新打开）。
- 预期节省：最多 12 × 单个子会话的体积。
- 风险：续聊时需要重新打开，有一次额外的磁盘读取。

**P1-6 RPC 的大负载不再重复发送（选择性开启）**

- 证据：G5。100 步产生 86 MB 事件，同一个结果发 5 遍。
- 方案：新增一个客户端能力位（`set_client_capabilities` 声明 `compact_events`）。开启后，`turn_end.toolResults`、`message_start`、`entry_appended` 不再携带已在 `message_end` 或 `tool_execution_end` 里发过的大内容。不开启时线路形状不变，不需要破坏性版本升级，但要同步 `docs/rpc.md`。
- 预期节省：协议流量和两端的序列化开销约 −80%。
- 风险：宿主（Armadra）需要适配。

### P2

1. **每次请求的 O(N) 转录复制**（`transform.ts:96-200`、`tree.ts:19`、`projection.ts:178`）：投影和 `convertToLlm` 按条目缓存，只处理新增部分。mock 下分配约 150 MB，CPU 收益更大。风险是 rewind、fork、压缩时需要让缓存失效。
2. **`Intl.Segmenter` 和 TUI 的 Unicode 正则惰性初始化**（`src/tui/ansi.ts:12`）：`-p`、RPC、ACP、`--version` 模式都能省约 3 MB RSS，`--version` 的 CPU 约少 16%。
3. **codemode 子进程加 `--max-old-space-size=256`**（`src/codemode/host-side.ts:178` 的参数）：防止脚本在超时前吃光内存（每个子进程基线约 59 MB）。需要确认权限模型下这些参数可用，Node 22/24 和 Electron 都要验证。
4. **图片被降级或压缩后在内存中释放 base64**：内存里的条目改为惰性引用（会话文件的字节偏移），rewind 或 fork 需要时再从 JSONL 读回。收益大，但实现复杂，牵涉 rewind/resume 语义，建议放在 P1-1 之后。
5. **bundle minify**：文件 −42%，源码字符串约 −2 MB，heapUsed 约 −1.4 MB，RSS 变化在噪声内。代价是报错堆栈可读性下降。性价比低。charset 改 ascii 无收益，不建议。
6. **V8 新生代参数**：mock 300 步无图时，默认参数的峰值是 366–487 MB，`--max-semi-space-size=8` 是 284 MB，`=4` 是 352 MB，`=1` 是 335 MB；user CPU 增加约 0–13%。机器当时有负载，波动大，**结论不确定**。
7. **fake 供应商**（`src/ai/fake/fake-provider.ts:215`）：CLI 默认实例不再记录完整上下文（测试可以显式开启）。不影响用户，但会让任何基于 `AMA_FAKE_SCRIPT` 的内存或性能测量偏大，300 步时偏差约 32 MB。

## 7. 复现

- `node scripts/bench-memory.mjs [场景…]`：`version`、`print`、`read-huge`、`resume`、`list`、`acp-pool`、`rpc-bytes`、`mock-http`，缺省全部，输出 Markdown 表（`--help` 看参数）。先 `pnpm build`；`--entry` 换被测入口。全部在临时目录里跑，不碰真实配置与会话，只用 fake 供应商和内置 mock 服务。
- `scripts/lib/mem-probe.cjs`：`--require` 预加载探针，环境变量 `AMA_MEM_LOG` / `AMA_MEM_INTERVAL` / `AMA_MEM_TAG` / `AMA_MEM_SNAP_EXIT` / `AMA_MEM_ALLOC`；收到 SIGUSR1 时（以 `--expose-gc` 启动的话）执行 GC 并记录一行；退出行带 `maxRss`。
- 堆快照与分配采样的分析用 Chrome DevTools 的 Memory 面板即可（报告写作时用的是自写的快照解析脚本，未入库）。
- TUI 场景（tmux 驱动）与真实模型场景没有进脚本：前者依赖终端，后者要花额度；它们的数字只在本报告与之后的 benchmarks 文档里记录。
